# План: school_stats.py — школьный журнал (SOLID)

Задача: мини-система для школы — журнал (студенты/предметы/оценки),
подсчёт статистики (средний балл по предмету и по ученику), консольные
уведомления при среднем балле ученика < 3.5. Требование задания —
разделение ответственности, расширяемость без правки существующего кода
(OCP), зависимость высокоуровневых сервисов от абстракций (DIP).

## Шаг 1. Доменные сущности (готово)

- `Student` — как минимум имя. Подумай: достаточно ли имени как
  уникального ключа (как в `basic/5_library` книги по названию), или
  нужен отдельный `id` (как `uuid4` в `6_crm.orders.new_order`) —
  на случай однофамильцев. Реши сам и коротко объясни себе почему.
- `Grade` — одна запись в журнале: ученик, предмет (`str` достаточно,
  отдельный класс `Subject` не обязателен), значение оценки. Подумай,
  каким типом хранить значение (`int` — оценки 1-5, или `float` —
  проще для среднего). Оба варианта рабочие, зависит от твоего вкуса.
- Оформи `Student` и `Grade` как `@dataclass` — здесь это уместнее
  голых классов с ручным `__init__`, посмотри как это делается.

## Шаг 2. `Journal` — только хранение (готово)

Единственная ответственность — держать данные и отдавать выборки, без
единой строчки подсчёта среднего (это чужая зона ответственности —
`Statistics`).

Нужны методы примерно такого назначения (сигнатуры/имена придумай
сам, тип возвращаемого значения — список чисел):

- добавить оценку (ученик, предмет, значение);
- получить все оценки конкретного ученика;
- получить все оценки по конкретному предмету;
- получить список всех учеников (понадобится `Monitoring` в шаге 5).

Подумай, в чём хранить данные внутри (`list[Grade]` и фильтрация по
атрибутам — самый простой вариант для старта). Для инициализации
пустого списка внутри `@dataclass` понадобится
`field(default_factory=list[Grade])` (мутабельные дефолты вроде `[]`
дата-класс запрещает) — это новый синтаксис, не встречавшийся раньше
в репо, отдельно не расписан ниже, раз уже применён в готовом коде.

Для каждого метода — конкретный образец в `basic/6_crm/orders.py`,
скелет один и тот же (`result: list[...] = []`, цикл, `if`-фильтр,
`.append`, `return result`):

- добавление записи в список — как `create_order`/`new_order` кладут
  новый заказ в список;
- фильтр по предмету/ученику — один в один `filter_by_tag`
  (`basic/6_crm/orders.py:133-139`): `for grade in ...: if <условие>:
  result.append(...)`;
- список уникальных учеников — тот же цикл, но условие на добавление
  другое: `if grade.student not in result`, вместо признака "заказ
  просрочен" как в `filter_overdue`.

## Шаг 3. Абстракция статистики

Здесь и заключается OCP: должно быть можно добавить новый алгоритм
подсчёта, не изменяя ни `Journal`, ни существующие реализации.

Этого паттерна (`abc.ABC`) в репозитории раньше не было — совсем новый
синтаксис, разберём отдельно. Абстрактный класс — это класс-контракт:
он сам не создаётся (`Foo()` от него упадёт с ошибкой), а описывает,
какие методы обязаны быть у всех "потомков". Игрушечный пример вне
контекста задания:

```python
from abc import ABC, abstractmethod


class Shape(ABC):
    @abstractmethod
    def area(self) -> float:
        ...


class Square(Shape):
    def __init__(self, side: float) -> None:
        self.side = side

    def area(self) -> float:
        return self.side ** 2
```

`Square()` работает, `Shape()` — нет (`TypeError: Can't instantiate
abstract class`). Любой код, ожидающий `Shape`, спокойно примет и
`Square`, и любой другой класс-наследник — это и есть точка
расширения.

Дальше — своими руками:

- 3.1. Абстрактный класс, например `Statistics(ABC)`, один
  `@abstractmethod` — принимает список оценок (`list[float]`, как
  решил в шаге 1), возвращает средний балл (`float`). Тело метода —
  `...`, как в примере выше.
- 3.2. Конкретный класс-наследник, например `MeanStatistics`, с
  реальной формулой среднего арифметического внутри метода.
- 3.3. Пока не пиши вторую реализацию (медиану и т.п.) — она нужна
  только в шаге 7, чтобы проверить, что интерфейс из 3.1 её выдержит
  без правок.

## Шаг 4. Абстракция уведомлений

Тот же приём `ABC` + `@abstractmethod`, что и в шаге 3 — только
абстракция другая.

- 4.1. Абстрактный класс, например `Notifier(ABC)`, один
  `@abstractmethod` — отправить уведомление (сам придумай сигнатуру:
  принимать ученика и средний балл, или готовую строку — как удобнее
  собирать сообщение).
- 4.2. Конкретная реализация, например `ConsoleNotifier` — внутри
  метода просто `print(...)`.

## Шаг 5. `Monitoring` — высокоуровневый сервис

Это компонент, который проверяет DIP на практике: класс принимает
готовые объекты через конструктор, а не создаёт их сам внутри. Ты уже
делал похожее в шаге 1 — `Grade.__init__` принимает готовый объект
`Student`, а не создаёт его сам. Здесь тот же приём, но вместо
`Student` в конструктор попадают объекты абстрактных типов
`Statistics` и `Notifier`.

- 5.1. Конструктор класса `Monitoring` принимает: объект типа
  `Statistics`, объект типа `Notifier`, и порог (например
  `threshold: float = 3.5` — с дефолтным значением, не хардкодить
  число внутри метода). Все три сохраняются в `self`, как обычные
  поля дата-класса.
- 5.2. Метод, условно "проверить всех учеников" — принимает `Journal`
  (или получает его тоже через конструктор, реши сам), и для каждого
  `Student` из `journal.get_students_list()`:
  - берёт его оценки через `journal.get_grades_by_student(...)`
    (готовый метод из шага 2);
  - считает средний балл вызовом метода из шага 3.1 на объекте
    `Statistics`, сохранённом в `self`;
  - если результат меньше `self.threshold` — вызывает метод из шага
    4.1 на объекте `Notifier`, сохранённом в `self`.
- 5.3. Проверь себя: внутри `Monitoring` нигде не должно быть
  `MeanStatistics()` или `ConsoleNotifier()` — только обращения к
  `self.statistics` / `self.notifier`. Создание конкретных объектов —
  снаружи, в шаге 6.

## Шаг 7. Проверка OCP на практике

Добавь вторую реализацию `Statistics` (например, медиану) и/или
вторую реализацию `Notifier` (например, "уведомление с восклицательным
знаком" или лог с префиксом) — **не меняя** код `Journal`,
`Monitoring` и уже существующих реализаций. Проверить это можно
буквально: подставить новый класс в шаг 6.3 вместо `MeanStatistics`
или `ConsoleNotifier` и убедиться, что `Monitoring` и `git diff`
по остальным классам после этого пустой. Если для этого пришлось
что-то править в старых классах — это сигнал, что абстракция в шаге
3.1 или 4.1 спроектирована неточно, стоит вернуться и поправить
интерфейс.
