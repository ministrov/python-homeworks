# План: school_stats.py — школьный журнал (SOLID)

Задача: мини-система для школы — журнал (студенты/предметы/оценки),
подсчёт статистики (средний балл по предмету и по ученику), консольные
уведомления при среднем балле ученика < 3.5. Требование задания —
разделение ответственности, расширяемость без правки существующего кода
(OCP), зависимость высокоуровневых сервисов от абстракций (DIP).

## Статус

- [ ] Шаг 1 — доменные сущности (`Student`, `Grade`)
- [ ] Шаг 2 — `Journal`: хранение и доступ к данным
- [ ] Шаг 3 — абстракция статистики + реализация среднего балла
- [ ] Шаг 4 — абстракция уведомлений + консольная реализация
- [ ] Шаг 5 — `Monitoring`: сервис, собирающий всё через DI
- [ ] Шаг 6 — demo-блок для ручной проверки
- [ ] Шаг 7 — проверка OCP: добавить вторую статистику/уведомление,
      не трогая существующие классы

## Шаг 1. Доменные сущности

- `Student` — как минимум имя. Подумай: достаточно ли имени как
  уникального ключа (как в `basic/5_library` книги по названию), или
  нужен отдельный `id` (как `uuid4` в `6_crm.orders.new_order`) —
  на случай однофамильцев. Реши сам и коротко объясни себе почему.
- `Grade` — одна запись в журнале: ученик, предмет (`str` достаточно,
  отдельный класс `Subject` не обязателен), значение оценки. Подумай,
  каким типом хранить значение (`int` — оценки 1-5, или `float` —
  проще для среднего). Оба варианта рабочие, зависит от твоего вкуса.
- Оформи `Student` и `Grade` как `@dataclass` — здесь это уместнее
  голых классов с ручным `__init__`, посмотри как это делается.

## Шаг 2. `Journal` — только хранение

Единственная ответственность — держать данные и отдавать выборки, без
единой строчки подсчёта среднего (это чужая зона ответственности —
`Statistics`).

Нужны методы примерно такого назначения (сигнатуры/имена придумай
сам, тип возвращаемого значения — список чисел):

- добавить оценку (ученик, предмет, значение);
- получить все оценки конкретного ученика;
- получить все оценки по конкретному предмету;
- получить список всех учеников (понадобится `Monitoring` в шаге 5).

Подумай, в чём хранить данные внутри (`list[Grade]` и фильтрация по
атрибутам — самый простой вариант для старта).

## Шаг 3. Абстракция статистики

Здесь и заключается OCP: должно быть можно добавить новый алгоритм
подсчёта, не изменяя ни `Journal`, ни существующие реализации.

- Абстрактный базовый класс (`abc.ABC` + `@abstractmethod`), один
  метод: принимает список оценок (`list[float]` или `list[int]` — как
  решил в шаге 1), возвращает средний балл (`float`).
- Одна конкретная реализация — среднее арифметическое.
- Оставь в голове (не реализуй сейчас) вторую гипотетическую
  реализацию — например, медиану — просто чтобы проверить, что
  интерфейс действительно это позволяет без правок. Реализуешь её в
  шаге 7.

## Шаг 4. Абстракция уведомлений

Симметрично шагу 3, но для уведомлений.

- Абстрактный базовый класс с одним методом — отправить уведомление
  (принимает то, что нужно для сообщения: ученика и его средний
  балл, либо готовую строку — выбери сам).
- Одна конкретная реализация — печать в консоль.

## Шаг 5. `Monitoring` — высокоуровневый сервис

Это компонент, который проверяет DIP на практике.

- Класс принимает в конструкторе **абстракции**, а не конкретные
  классы: объект типа "статистика" и объект типа "уведомления"
  (плюс, если нужно, порог 3.5 — как параметр с дефолтным значением,
  не хардкод внутри метода).
- Метод примерно "проверить всех учеников": для каждого ученика из
  `Journal` берёт его оценки, считает средний балл через переданную
  статистику, и если ниже порога — вызывает переданный notifier.
- Важно: `Monitoring` не должен внутри себя писать
  `MeanStatistics()` или `ConsoleNotifier()` — эти объекты создаются
  снаружи и передаются внутрь. Это и есть DIP на практике.

## Шаг 6. Demo-блок

По аналогии с `intermediate/3_oop_base` (блок демонстрации в конце
файла под `if __name__ == "__main__":`):

- создать несколько `Student`;
- заполнить `Journal` оценками (включая хотя бы одного ученика со
  средним < 3.5, чтобы уведомление реально сработало);
- собрать `Monitoring` с конкретными реализациями статистики и
  уведомлений;
- запустить проверку и убедиться, что консоль печатает уведомление
  только для нужного ученика.

## Шаг 7. Проверка OCP на практике

Добавь вторую реализацию `Statistics` (например, медиану) и/или
вторую реализацию `Notifier` (например, "уведомление с восклицательным
знаком" или лог с префиксом) — **не меняя** код `Journal`,
`Monitoring` и уже существующих реализаций. Если для этого пришлось
что-то править в старых классах — это сигнал, что абстракция в шаге 3
или 4 спроектирована неточно, стоит вернуться и поправить интерфейс.

## Типизация под Pylance strict

- Аннотируй сигнатуры абстрактных методов (`ABC`) полностью — тело
  `...` или `raise NotImplementedError`, но типы параметров и
  возврата обязательны.
- `list[Grade]`, `list[float]` и т.д. — по аналогии с `list[float]` в
  `basic/4_expenses`.
